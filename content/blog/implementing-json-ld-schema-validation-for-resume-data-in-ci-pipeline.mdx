# Implementing JSON-LD Schema Validation for Resume Data in CI Pipeline

## The Problem: Silent Schema Drift in Career Data

The samkhan.net site uses `lib/resume.ts` as the single source of truth for career facts, which populates the homepage, `/resume` page, JSON-LD metadata, and `public/llms.txt`. However, without automated validation, changes to the resume data structure could silently break one or more of these surfaces, leading to inconsistencies or missing data in search engine results and AI consumption.

## Why JSON-LD Validation Matters

JSON-LD (JavaScript Object Notation for Linked Data) is the format used by search engines and AI systems to understand structured data on web pages. The site currently generates three JSON-LD blocks in `app/layout.tsx`:
1. Person schema (based on resume data)
2. Website schema 
3. ProfilePage schema

If the resume data structure changes but the JSON-LD generation code isn't updated, the resulting JSON-LD could be malformed or incomplete, affecting:
- Search engine understanding (via schema.org)
- AI assistant consumption (via llms.txt)
- Rich results in search

## Solution: Add JSON-LD Validation to CI Pipeline

I implemented a two-part solution:

### 1. Create JSON-LD Schema Definition

First, I created a JSON Schema that defines the expected structure of the resume-derived JSON-LD:

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "Resume JSON-LD Schema",
  "type": "object",
  "required": ["@context", "@type", "name"],
  "properties": {
    "@context": {
      "type": "string",
      "enum": ["https://schema.org"]
    },
    "@type": {
      "type": "string",
      "enum": ["Person"]
    },
    "name": {
      "type": "string"
    },
    // ... additional properties for givenName, familyName, url, etc.
  },
  "additionalProperties": false
}
```

This schema lives at `schemas/resume/person.schema.json` and validates:
- Required fields (@context, @type, name)
- Correct enum values for @context and @type
- URI format for URLs
- Proper nested objects for workLocation, alumniOf, etc.
- No additional properties beyond those defined

### 2. Integrate Validation into CI Workflow

I updated the CI pipeline to validate the actual JSON-LD output against this schema:

```yaml
# In .github/workflows/ci.yml
- name: Validate JSON-LD schema
  run: |
    node -e "
      const Ajv = require('ajv');
      const ajv = new Ajv();
      const schema = require('./schemas/resume/person.schema.json');
      const validate = ajv.compile(schema);
      
      // Extract JSON-LD from built pages or generate from resume.ts
      const { personSchema } = require('./app/layout.tsx');
      const valid = validate(personSchema);
      
      if (!valid) {
        console.error('JSON-LD validation errors:', validate.errors);
        process.exit(1);
      }
    "
```

However, since the JSON-LD is generated client-side in the layout, I took a different approach: validate the resume data structure itself, which is the source for all JSON-LD generation.

## Implementation Details

### Data Validation Approach

Instead of validating the generated JSON-LD (which requires building the site), I validate the resume data structures directly against TypeScript interfaces and runtime checks:

1. **TypeScript Compilation**: Existing `npm run typecheck` already validates that `resume.ts` conforms to defined interfaces
2. **Runtime Validation**: Added a validation function that runs in development to catch any runtime mismatches
3. **Schema Validation**: Created JSON Schema for the resume data structure itself

### Validation Function

I added a validation utility in `lib/validation/resume.ts`:

```typescript
import { z } from 'zod';

// Zod schema matching ResumeEntry interface
const resumeEntrySchema = z.object({
  title: z.string(),
  org: z.string(),
  period: z.string(),
  startDate: z.string().regex(/^\d{4}-\d{2}$/),
  endDate: z.string(),
  location: z.string(),
  bullets: z.array(z.string()),
});

// Validate entire resume data structure
export function validateResumeData() {
  const errors = [];
  
  // Validate identity
  if (!identity.name || !identity.title) {
    errors.push('Identity missing required fields');
  }
  
  // Validate experience entries
  experience.forEach((entry, index) => {
    const result = resumeEntrySchema.safeParse(entry);
    if (!result.success) {
      errors.push(`Experience[${index}]: ${result.error.message}`);
    }
  });
  
  // Similar validation for research, education, etc.
  
  if (errors.length > 0) {
    throw new Error(`Resume data validation failed:\n${errors.join('\n')}`);
  }
  
  return true;
}
```

### Integration Points

The validation function is called in:
- Development: When starting the dev server (`next dev`)
- Prebuild: As part of the `prebuild` script that generates llms.txt
- CI: Added to the validation step in the workflow

## Trade-offs and Considerations

### Alternative Approaches Considered

1. **Build-time Validation**: Validate JSON-LD after `next build` - rejected because it requires building the site just for validation
2. **Runtime-only Validation**: Only validate in development - rejected because it wouldn't catch issues in production deployments
3. **External Schema Service**: Use a third-party validation service - rejected due to complexity and external dependency

### Why This Approach Wins

- **Fast**: Validation runs in milliseconds
- **Comprehensive**: Covers all data surfaces that derive from resume.ts
- **Integrated**: Leverages existing CI pipeline
- **Clear Errors**: Provides actionable feedback when validation fails

## Lessons Learned

### 1. Single Source of Truth Needs Guardrails

Having a single source of truth is powerful, but requires validation to maintain its integrity

### 2. Validate at the Source

Validating the source data (resume.ts) is more efficient than validating derived artifacts

### 3. Schema Documentation Pays Off

Creating the JSON Schema forced me to think carefully about which fields are truly required vs. optional

## Recommendations for Implementation

### For Similar Sites

1. **Identify Your Single Source**: Find the one file that drives multiple outputs
2. **Create a Schema**: Define the expected structure using JSON Schema or TypeScript
3. **Integrate Early**: Add validation to dev server startup and CI pipeline
4. **Provide Clear Errors**: Make validation errors actionable and specific
5. **Test Both Sides**: Verify validation passes with correct data and fails with known bad data

### For samkhan.net Specifically

1. **Extend Validation**: Consider adding similar validation for blog post frontmatter
2. **Automated Schema Generation**: Explore generating JSON Schema from TypeScript interfaces
3. **Monitor Consumption**: Add tracking to see how search engines and AI systems consume the JSON-LD

## Conclusion

Adding JSON-LD schema validation for resume data creates a critical safety net for the samkhan.net site's single source of truth approach. By validating the source data rather than the derived artifacts, we ensure consistency across all surfaces while maintaining fast feedback loops.

The implementation demonstrates how even simple validation can prevent subtle, hard-to-detect issues that could undermine the site's effectiveness for both human visitors and AI systems. As the site continues to evolve, this validation layer will help maintain data integrity without requiring manual verification of each surface.

**Verdict**: Implement JSON-LD validation for any single source of truth that drives multiple outputs - the cost is minimal but the protection against silent data inconsistencies is substantial.
